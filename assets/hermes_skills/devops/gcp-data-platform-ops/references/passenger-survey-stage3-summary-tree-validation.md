# Passenger survey Stage3 summary-tree validation and fast repair

Use when a BigQuery-backed dashboard has a valid `metrics_tree` but `summary_tree` is empty, slow to regenerate, or suspected to have a different hierarchy shape than `metrics_tree`.

## Durable lesson

Stage3 dashboard snapshots need two separate readiness checks:

1. `metrics_tree` correctness: counts, scoring fields, mapped/unmapped rows, and fixed-depth product/tour leaves.
2. `summary_tree` shape correctness: the `children` keys must match `metrics_tree` at every level, even if summaries are generated by a cheaper method.

For large passenger-survey months, full post-order Gemini summarization can be impractically slow because it may call the model once per leaf/branch node. Do not block a production dashboard structural fix on full Gemini if the immediate requirement is tree shape and drilldown correctness.

## Safe fallback pattern

1. Query the latest formal snapshot and confirm the problem:
   - `summary_tree` is empty or too small, or
   - a known drilldown path is missing, or
   - node counts/child keys differ between `metrics_tree` and `summary_tree`.
2. Run Stage3 against the formal source table and date window.
3. Intercept the append step so you can validate before writing.
4. Replace only the summary builder with a deterministic extractive builder that:
   - preserves the exact input organizational tree shape;
   - returns branch/leaf objects with `kind`, `path`, `summary`, `opinion_count`, and `children` for branches;
   - uses short source-text excerpts or child summaries; and
   - records a non-Gemini `summary_model`, e.g. `deterministic-extractive-v1`.
5. Validate before append:
   - recursive child-key equality between `metrics_tree` and `summary_tree`;
   - equal node counts;
   - non-empty root summary when source has rows;
   - known business-critical path(s), e.g. `region -> group -> line -> tour_name -> tour_code`;
   - mapped vs unmapped row counts.
6. Append the validated row, then query BigQuery back and repeat the same checks on the stored JSON.

## Example verification snippets

Recursive shape check:

```python
def count_nodes(node):
    if not isinstance(node, dict):
        return 0
    return 1 + sum(count_nodes(c) for c in (node.get("children") or {}).values() if isinstance(c, dict))


def first_shape_mismatch(metrics_node, summary_node, path=()):
    mc = metrics_node.get("children") or {}
    sc = summary_node.get("children") or {}
    if set(mc) != set(sc):
        return path
    for key in mc:
        mismatch = first_shape_mismatch(mc[key], sc[key], path + (key,))
        if mismatch is not None:
            return mismatch
    return None
```

Known-path check:

```python
node = summary_tree
for part in [region, group, line, tour_name, tour_code]:
    node = (node.get("children") or {}).get(part)
    if not isinstance(node, dict):
        raise RuntimeError(f"missing summary_tree path at {part}")
```

## BigQuery JSON caution

When writing through `insert_rows_json`, use the existing helper that serializes JSON fields for streaming inserts. When loading via `load_table_from_json`, pass nested dict/list values for JSON columns. Always query the written row back because BigQuery can accept JSON-looking strings that later break `JSON_VALUE`/drilldown expectations.

## Reporting format

Report the final row handle and structural checks compactly:

- `run_id`
- project/dataset/table
- date window
- source row count, mapped count, unmapped count
- `metrics_nodes` vs `summary_nodes`
- first mismatch or `None`
- root summary length
- known path validation result

Avoid presenting deterministic extractive summaries as semantic Gemini-quality analysis. Say explicitly that this is a structural/dashboard repair and offer a later quality pass for upper-level Gemini summaries if needed.
