# 機票比價

查 BigQuery `dev-cola-rd.economy` 裡各旅行社的機票票價並比較。全部用 `bigquery_query` 工具執行，唯讀。

## 唯讀：只能查，不能改資料

`bigquery_query` **只做查詢，沒有新增、刪除、修改資料的能力**。工具只開放
`list_datasets`／`list_tables`／`describe_table`／`query` 四個動作，而且每句 SQL 都會先
dry run，由 BigQuery 判定語句型別，不是 `SELECT` 一律拒絕。

所以：使用者要求改價、寫回、刪除或新增任何資料時，**直接說明這個工具只能查詢**，
不要嘗試寫 `INSERT`／`UPDATE`／`DELETE`／`MERGE`／`CREATE`／`EXPORT DATA`，那些只會被擋下來。

## 對話流程（依序照做，不要跳步）

第 2 步與第 3 步是兩條分支：使用者給的是**具體日期**走第 2 步，給的是**模糊範圍**（暑假、旺季、過年）走第 3 步。兩條都收斂到具體日期後才進第 4 步。

### 第 1 步：使用者沒給日期或航點時，先問

使用者說「幫我比機票」但沒講日期跟目的地時，**不要猜、也不要直接查**。先給他可選的範圍，請他挑：

1. **可查日期** —— 不要憑印象回答，也不要照抄本文件的快照。執行「查可用日期」那段 SQL 拿到當下真實的日期清單，只列出**今天起一年內**的。
2. **可查航點** —— 出發地固定是台北（TPE），使用者要選的是目的地。直接列下面那份清單。

**只講城市不算講清楚航點。** 使用者只指定地點、沒指定機場時（例如「東京的機票」「幫我看大阪」），
先問他要查哪一個機場、還是兩個都要一起查，拿到答案再往下走。不要自己挑一個機場當作他的意思——
同一個城市不同機場的票價與航班完全不同，挑錯了結果不會報錯，使用者也看不出來被換掉了。
哪些城市有多個機場見「可查航點」那節。

拿到日期與航點後再往下走。

### 第 2 步：確認該日期真的有資料

使用者給的日期若不在清單裡（很常見，見「日期是離散的」），**明確告訴他該日期沒有資料**，並列出一年內實際可查的日期讓他改選。不要自作主張換成鄰近日期。

### 第 3 步：問題不夠具體時，先收斂範圍再查

使用者拿現有資料做**標準比價以外的分析**時（「暑假哪家便宜」「哪種天數組合最划算」「這幾個月怎麼走比較省」），提問通常帶著模糊的範圍詞：暑假、旺季、過年、連假、下個月、最近、便宜的時候。

**不要自己幫那個詞下定義就開查。** 你以為的暑假是 7–8 月，使用者可能算到 6 月底；查完才發現定義不同，7.5 GB 就白掃了。

流程是「**問定義 → 查範圍有多大 → 給使用者確認 → 才跑分析**」，三個回合內講完。

#### 3-1 先問模糊詞的定義

一次問完、給選項，不要開放式問「你想怎麼看」：

> 使用者：請把暑假有的天數組合整理給我，列出各旅行社的費用優惠順序
>
> 先確認兩件事再查：
>
> 1. 暑假指哪個範圍？
>    ・**7–8 月**（最常見）
>    ・**6–8 月**（含期末那段）
>    ・你有指定的起訖日
> 2. 目的地是哪裡？出發地固定台北。

#### 3-2 先查「有幾組」，報給使用者確認

定義確定後，**先跑一支只回聚合值的探索查詢**，不要直接跑比價。使用者這時要的是「我有幾個選擇」，不是幾千列明細：

```sql
SELECT DATE_DIFF(PARSE_DATE('%Y/%m/%d', `返回日期`),
                 PARSE_DATE('%Y/%m/%d', `出發日期`), DAY) + 1 AS `天數`,
       COUNT(DISTINCT CONCAT(`出發日期`, '~', `返回日期`)) AS `日期組合數`,
       MIN(`出發日期`) AS `最早出發`, MAX(`出發日期`) AS `最晚出發`
FROM `dev-cola-rd.economy.cola_air_tickets_price_temporary_table`
WHERE `出發日期` BETWEEN '2026/07/01' AND '2026/08/31'
  AND COALESCE(`去程降落機場3`, `去程降落機場2`, `去程降落機場1`) = 'NRT'
  AND `去程艙等與艙等編碼1` LIKE '經濟艙%'
GROUP BY `天數`
ORDER BY `日期組合數` DESC
```

只查可樂一張表，掃描量遠低於全六家比價的 7.5 GB，而且回傳不到 10 列。回覆長這樣：

> 暑假（7/1–8/31）飛東京成田，可樂共有 **34 組去回日期組合**，分成 5 種天數：
>
> ・5 天｜12 組　・4 天｜9 組　・6 天｜7 組　・7 天｜4 組　・3 天｜2 組
>
> 全部一起比會超過能列的量。要看哪兩種天數？

**組數一定要講出來。** 使用者說「假設兩組」時，他心裡沒有母數；先告訴他總共 34 組，他才知道自己在從多少裡面挑。

#### 3-3 使用者挑完才跑比價

挑定之後回到第 4 步的可樂錨點比價，`WHERE` 換成那幾種天數對應的日期，一樣一次最多 10 個航班組。

#### 衍生欄位要自己算：天數

`出發日期`／`返回日期` 都是 STRING（地雷 4），算天數要先 `PARSE_DATE`，而且**兩種 schema 的格式字串不同**：

| 來源 | 日期欄位 | PARSE_DATE 格式 |
|---|---|---|
| 可樂 | `出發日期`／`返回日期` | `'%Y/%m/%d'` |
| 四家 OTA | `去程日期`／`回程日期` | `'%Y-%m-%d'` |

天數用「含頭含尾」：`DATE_DIFF(回程, 去程, DAY) + 1`，5 天 4 夜算 5 天。回覆一律講「幾天」不講「幾晚」，跟業務端口徑一致。

#### 這些情況不用問

| 情況 | 做法 |
|---|---|
| 使用者已經給具體日期 | 直接走第 4 步，不要再問範圍 |
| 使用者自己限縮過（「挑兩組就好」） | 照他說的做，只補問缺的那一半 |
| 範圍算出來只有 1–2 組 | 不用確認，直接查完給結果 |
| 只是要確認「有沒有資料」 | 查一張小表數個數就好 |

**探索查詢一律只回聚合值，不回明細列。** 數量、範圍、分組是給使用者做決定用的；明細等他挑完再撈。這一步就撈明細，等於把之後要撈的東西先白撈一次。

### 第 4 步：查價並比較

**預設用「可樂錨點比價」，一次最多列 10 個航班組。** 只列可樂有賣的行程，其他家用相同航班與艙等配對。這是絕大多數情況要的：「我們有這個行程，別人賣多少」。

以可樂有的為準，不是以市場全貌為準 —— 可樂沒賣的行程預設不出現。只有使用者明確說要看「市場上還有什麼更便宜的」「可樂沒有的也要」時，才改用「全市場比價」。

### 第 5 步：回覆使用者

每一筆至少要有這些欄位：

**去程日期、回程日期、去程航班編號、回程航班編號、去程艙等、回程艙等、機票價錢、稅金**

另外一定要標明**哪一家旅行社**、**含稅總價**（機票價錢＋稅金），錨點比價還要給**與可樂的價差**。使用者要比的是總價，不是票面價。

**結果幾乎一定會超過你列得完的數量，絕對不要讓使用者以為看到的就是全部。** 實測單一日期單一航點的經濟艙就有上千筆配對（2027-01-24 → NRT 共 1,217 筆）。所以：

1. **一次最多列 10 個航班組**，用主要模式那段的 `QUALIFY DENSE_RANK() ... <= 10`。一組會展開成 3~5 列（每家旅行社一列），10 組實測 36 列。使用者說要更多，再往上調那個數字。
2. **先講總量再列明細**，單位用「組」不用「筆」：「共配對到 383 個航班組、1,217 筆報價，以下是價差最大的 10 組」。使用者要挑的是航班組合，逐筆列數對他沒有意義。
3. **使用者要看全貌時給每家的彙總，不要硬展開明細。** 彙總比逐筆列舉有用得多：

```sql
SELECT `他`.`旅行社`,
       COUNT(*) AS `配對筆數`,
       COUNTIF((`他`.`機票價錢`+`他`.`稅金`) < (`可`.`機票價錢`+`可`.`稅金`)) AS `比可樂便宜`,
       COUNTIF((`他`.`機票價錢`+`他`.`稅金`) > (`可`.`機票價錢`+`可`.`稅金`)) AS `比可樂貴`,
       MIN((`他`.`機票價錢`+`他`.`稅金`) - (`可`.`機票價錢`+`可`.`稅金`)) AS `最大價差`
-- 其餘 FROM / JOIN 與下方主查詢相同
GROUP BY `他`.`旅行社`
```

4. `QUALIFY` 與 `LIMIT` 都只是控制回傳量，**不是**代表資料只有這些。工具回傳的 `truncated` 為 true 時更要講明。

## 欄位對照：兩種 schema，不能混用

四家 OTA（東南／雄獅／易遊／山富）欄位一致；可樂那張表完全不同：

| 意義 | 四家 OTA | 可樂 |
|---|---|---|
| 去程日期 | `去程日期` | `出發日期` |
| 回程日期 | `回程日期` | `返回日期` |
| 去程艙等 | `去程艙等1` | `去程艙等與艙等編碼1` |
| 回程艙等 | `回程艙等1` | `回程艙等與艙等編碼1` |
| 機票價錢 | `票面價格` | `基礎票價` |
| 稅金 | `稅金` | `稅金` |
| 去程航班編號 | `去程航班編號1` | `去程航班編號1` |
| 回程航班編號 | `回程航班編號1` | `回程航班編號1` |
| 出發／抵達機場 | **沒有這個欄位** | `去程起飛機場1` … `去程降落機場3` |

航班編號、艙等、機場都有 `1`／`2`／`3` 三組，代表轉機的第一、二、三段。直飛只有第 1 段有值。

## 四個一定會踩的地雷

### 1. `去程降落機場1` 不是目的地

這是最容易錯、而且錯了不會報錯的一個。**`去程降落機場1` 只是第一段的降落點。** 實測 2026-11-24：第一段降落 NRT 的 5,930 筆裡，只有 2,936 筆（49.5%）真的是去東京，另一半是**經東京轉機**去 SFO、LAX、SEA、CDG、HKG。用它當目的地會把美國線的票混進東京線，價格瞬間爆掉。

目的地一律這樣取：

```sql
COALESCE(`去程降落機場3`, `去程降落機場2`, `去程降落機場1`)
```

出發地用 `去程起飛機場1` 則是正確的（第一段的起飛點就是出發地）。

### 2. 比價一定要含艙等，否則是在比不同東西

可樂同一個日期、同一個航點就橫跨經濟艙到頭等艙。實測 TPE→NRT 直飛，`基礎票價` 從 `經濟艙Q` 的 8,885 一路到 `頭等艙A` 的 125,000。**只用航班編號配對，會拿可樂的商務艙去比別家的特價經濟艙**，算出來的價差毫無意義。

配對鍵一定要包含去程艙等與回程艙等。艙等格式是「艙別＋艙等代碼」：

- 經濟艙、商務艙、頭等艙：兩邊格式相同（`經濟艙Q`、`商務艙J`、`頭等艙A`），可直接等值配對
- **豪華經濟艙兩邊寫法不同**：可樂是 `豪經艙D`，OTA 是 `豪華經濟艙D`。要比這個艙等得先正規化，否則永遠配不到

只想看經濟艙時加 `WHERE 去程艙等... LIKE '經濟艙%'`。

### 3. 中文欄位名「和中文別名」都要反引號

BigQuery 的非 ASCII 識別碼一律要反引號，**別名也算**。漏了會直接語法錯誤：

```sql
SELECT MIN(去程日期) AS 最早          -- ✗ Illegal input character
SELECT MIN(`去程日期`) AS `最早`      -- ✓
```

### 4. 可樂的日期是斜線，OTA 是破折號

- 可樂：`2026/11/24`
- 四家 OTA：`2026-11-24`

兩者都是 **STRING 不是 DATE**。跨表比較時統一成破折號格式：

```sql
REPLACE(`出發日期`, '/', '-')
```

但要注意：**`WHERE` 條件必須用該表原本的格式**，不能用轉換後的。查可樂就得寫斜線：

```sql
WHERE `出發日期` = '2027/01/24'   -- ✓ 可樂，830 筆
WHERE `出發日期` = '2027-01-24'   -- ✗ 可樂，0 筆（不會報錯，只是靜靜地什麼都沒有）
WHERE `去程日期` = '2027-01-24'   -- ✓ 四家 OTA
```

這個錯誤不會噴任何錯誤訊息，只會回空結果，很容易被誤判成「那天沒資料」。

## 日期是離散的，不是連續區間

資料只有爬蟲實際抓過的那些日子，不是一段連續期間。各表的日期集合也**不一樣**，山富最密、可樂最疏。所以：

- 絕對不要假設「某月整個月都查得到」
- 使用者給的日期沒資料是常態，要直接講明並給實際可選清單

### 查可用日期

回答「有哪些日期可查」時跑這段，取今天起一年內。**日期用 `STRING_AGG` 聚成一列，不要一天回一列**（理由見下）：

```sql
WITH `所有日期` AS (
  SELECT REPLACE(`出發日期`, '/', '-') AS `日期`, '可樂' AS `來源`
  FROM `dev-cola-rd.economy.cola_air_tickets_price_temporary_table`
  UNION ALL SELECT `去程日期`, '東南' FROM `dev-cola-rd.economy.New_settour_air_tickets_price`
  UNION ALL SELECT `去程日期`, '雄獅' FROM `dev-cola-rd.economy.New_Lion_air_tickets_price`
  UNION ALL SELECT `去程日期`, '易遊' FROM `dev-cola-rd.economy.New_Eztravel_air_tickets_price`
  UNION ALL SELECT `去程日期`, '山富' FROM `dev-cola-rd.economy.New_richmond_air_tickets_price`
),
`每日來源數` AS (
  SELECT `日期`, COUNT(DISTINCT `來源`) AS `幾家有`
  FROM `所有日期`
  WHERE `日期` BETWEEN FORMAT_DATE('%Y-%m-%d', CURRENT_DATE())
                   AND FORMAT_DATE('%Y-%m-%d', DATE_ADD(CURRENT_DATE(), INTERVAL 1 YEAR))
  GROUP BY `日期`
)
SELECT `幾家有`,
       COUNT(*) AS `日期數`,
       STRING_AGG(`日期` ORDER BY `日期`) AS `日期清單`
FROM `每日來源數`
GROUP BY `幾家有`
ORDER BY `幾家有` DESC
```

最多回 5 列（`幾家有` 只可能是 1–5），而且「五家都有的日期」跟「只有一家有的日期」一次分好，不必再跑第二趟。

**為什麼一定要聚合：`BQTOOL_MAX_ROWS` 是 300。** 一天回一列的話，只要爬蟲抓過的日期超過 300 個，回傳就會被默默截斷（`truncated=true`）。而第 2 步整個邏輯是「使用者給的日期不在清單裡 → 明確告訴他沒有資料」—— 清單被截斷，模型就會拿一份不完整的清單去斷言「那天沒資料」。**講錯了不會報錯**，跟地雷 1、地雷 4 是同一種失敗模式。聚合成 5 列以內就永遠踩不到上限。

掃描量完全不變（一樣掃那五張表的日期欄），省的純粹是回傳量與誤答風險。

想省成本、只是要粗略確認範圍時，改查單一張表的 `MIN`／`MAX`／`COUNT(DISTINCT)` 就好。

## 主要模式：可樂錨點比價

只列**可樂有賣**的行程，其他家用「相同去回航班＋相同艙等」配對。這樣航點來自可樂的真實機場欄位，不是推導；而且比的是同一趟飛機的同一個艙位。

把 `'2026-11-24'`、`'2026/11/24'`、`'NRT'` 換成使用者指定的值。這段已實測可用：

```sql
WITH `可樂行程` AS (
  SELECT REPLACE(`出發日期`, '/', '-') AS `去程日期`,
         REPLACE(`返回日期`, '/', '-') AS `回程日期`,
         `去程航班編號1` AS `去程航班`, `回程航班編號1` AS `回程航班`,
         `去程艙等與艙等編碼1` AS `去程艙等`, `回程艙等與艙等編碼1` AS `回程艙等`,
         COALESCE(`去程降落機場3`, `去程降落機場2`, `去程降落機場1`) AS `航點`,
         MIN(`基礎票價`) AS `機票價錢`, MIN(`稅金`) AS `稅金`
  FROM `dev-cola-rd.economy.cola_air_tickets_price_temporary_table`
  WHERE `出發日期` = '2026/11/24'
    AND COALESCE(`去程降落機場3`, `去程降落機場2`, `去程降落機場1`) = 'NRT'
    AND `去程艙等與艙等編碼1` LIKE '經濟艙%'
  GROUP BY `去程日期`, `回程日期`, `去程航班`, `回程航班`, `去程艙等`, `回程艙等`, `航點`
),
`其他家` AS (
  SELECT '東南' AS `旅行社`, `去程日期`, `回程日期`,
         `去程航班編號1` AS `去程航班`, `回程航班編號1` AS `回程航班`,
         `去程艙等1` AS `去程艙等`, `回程艙等1` AS `回程艙等`,
         `票面價格` AS `機票價錢`, `稅金`
  FROM `dev-cola-rd.economy.New_settour_air_tickets_price`
  WHERE `去程日期` = '2026-11-24'
  UNION ALL
  SELECT '雄獅', `去程日期`, `回程日期`, `去程航班編號1`, `回程航班編號1`,
         `去程艙等1`, `回程艙等1`, `票面價格`, `稅金`
  FROM `dev-cola-rd.economy.New_Lion_air_tickets_price`
  WHERE `去程日期` = '2026-11-24'
  UNION ALL
  SELECT IF(`海外供應商`, '易遊(海外)', '易遊(國內)'), `去程日期`, `回程日期`,
         `去程航班編號1`, `回程航班編號1`, `去程艙等1`, `回程艙等1`, `票面價格`, `稅金`
  FROM `dev-cola-rd.economy.New_Eztravel_air_tickets_price`
  WHERE `去程日期` = '2026-11-24'
  UNION ALL
  SELECT '山富', `去程日期`, `回程日期`, `去程航班編號1`, `回程航班編號1`,
         `去程艙等1`, `回程艙等1`, `票面價格`, `稅金`
  FROM `dev-cola-rd.economy.New_richmond_air_tickets_price`
  WHERE `去程日期` = '2026-11-24'
),
`其他家最低` AS (
  SELECT `旅行社`, `去程日期`, `回程日期`, `去程航班`, `回程航班`,
         `去程艙等`, `回程艙等`,
         MIN(`機票價錢`) AS `機票價錢`, MIN(`稅金`) AS `稅金`
  FROM `其他家`
  GROUP BY `旅行社`, `去程日期`, `回程日期`, `去程航班`, `回程航班`, `去程艙等`, `回程艙等`
),
`配對` AS (
  SELECT `可`.`航點`, `可`.`去程日期`, `可`.`回程日期`,
         `可`.`去程航班`, `可`.`回程航班`, `可`.`去程艙等`, `可`.`回程艙等`,
         `他`.`旅行社`, `他`.`機票價錢`, `他`.`稅金`,
         `他`.`機票價錢` + `他`.`稅金` AS `含稅總價`,
         `可`.`機票價錢` + `可`.`稅金` AS `可樂含稅總價`,
         (`他`.`機票價錢` + `他`.`稅金`) - (`可`.`機票價錢` + `可`.`稅金`) AS `價差`
  FROM `可樂行程` AS `可`
  JOIN `其他家最低` AS `他`
    ON `可`.`去程日期` = `他`.`去程日期`
   AND `可`.`回程日期` = `他`.`回程日期`
   AND `可`.`去程航班` = `他`.`去程航班`
   AND `可`.`回程航班` = `他`.`回程航班`
   AND `可`.`去程艙等` = `他`.`去程艙等`
   AND `可`.`回程艙等` = `他`.`回程艙等`
),
`組內最佳` AS (
  SELECT *, MIN(`價差`) OVER (
    PARTITION BY `去程航班`, `回程航班`, `去程艙等`, `回程艙等`
  ) AS `該組最大節省`
  FROM `配對`
)
SELECT * EXCEPT(`該組最大節省`)
FROM `組內最佳`
QUALIFY DENSE_RANK() OVER (
  ORDER BY `該組最大節省`, `去程航班`, `回程航班`, `去程艙等`, `回程艙等`
) <= 10
ORDER BY `該組最大節省`, `價差`
```

`價差` 為負代表該家比可樂便宜。要「哪些行程我們賣得比別人貴」就照 `價差` 升冪看前幾筆；要「我們哪裡有優勢」就降冪。

### 要限制數量時，限「組」不要限「列」

最後那段 `QUALIFY DENSE_RANK() ... <= 10` 是刻意不用 `LIMIT` 的。一組行程會展開成 3~5 列（每家旅行社一列），所以 `LIMIT 30` 實際上只剩 6~10 組，而且**組數會隨每組配對到幾家而浮動**，無法指定「給我 10 組」。

用 `QUALIFY DENSE_RANK()` 才是先挑出 10 組行程、再把每組所有旅行社完整帶出（實測 10 組 = 36 列）。要幾組就改那個數字。

兩個寫法上的坑：

- **不能把分析函數塞進 window 的 `ORDER BY`**，`ORDER BY MIN(價差) OVER (...)` 會噴 `Analytic function not allowed in Window ORDER BY`。要像上面那樣先用一個 CTE 算出 `該組最大節省`，再拿它排序。
- `DENSE_RANK` 的 `ORDER BY` 要加上航班與艙等當決勝欄位，否則同分的組會被算成同一名，實際取回的組數會超出預期。

### 配對率（實測 2026-11-24 / NRT，可樂共 383 個不重複去回行程）

| 旅行社 | 配對到 | 配對率 |
|---|---|---|
| 雄獅 | 260 | 68% |
| 東南 | 225 | 59% |
| 山富 | 224 | 58% |
| 易遊（國內） | 169 | 44% |
| 易遊（海外） | 21 | 5% |

配不到不是錯誤，是那家真的沒賣這個組合（易遊海外貨源本來就少）。回覆時可以說明某家沒有可比對的行程，不要假裝它沒有報價。

## 次要模式：全市場比價

使用者明確要看「可樂沒有的也算」時才用。因為 OTA 表沒有機場欄位，只能拿可樂表推航線：先撈出「飛某目的地的航班編號集合」，再用 `IN` 篩 OTA。

```sql
WITH `目的地航班` AS (
  SELECT DISTINCT `去程航班編號1` AS `航班`
  FROM `dev-cola-rd.economy.cola_air_tickets_price_temporary_table`
  WHERE COALESCE(`去程降落機場3`, `去程降落機場2`, `去程降落機場1`) = 'NRT'
)
SELECT '山富' AS `旅行社`, `去程日期`, `回程日期`, `去程航班編號1`, `回程航班編號1`,
       `去程艙等1`, `回程艙等1`, `票面價格`, `稅金`,
       `票面價格` + `稅金` AS `含稅總價`
FROM `dev-cola-rd.economy.New_richmond_air_tickets_price`
WHERE `去程日期` = '2026-11-24'
  AND `去程航班編號1` IN (SELECT `航班` FROM `目的地航班`)
ORDER BY `含稅總價`
LIMIT 30
```

這是推導不是事實，有兩個限制要誠實面對：

- 少數航班編號對到兩條航線（例如 `BR067` 同時出現 TPE-LHR 與 TPE-BKK），可能混進不相干的結果
- 可樂沒收錄的航班就對照不到，那筆會被漏掉

用這個模式回覆時，要告訴使用者航點是用航班編號推得的。

## 成本控制：這件事很重要

這些表**沒有做分區**，所以 `WHERE` 完全不會減少掃描量。掃多少只由「選了幾個欄位 × 全表列數」決定。實測（2026-08-20）：

| 來源 | 列數 | 單家掃描量 |
|---|---|---|
| 可樂 | 736 萬 | 615 MB |
| 東南 | 1,083 萬 | 850 MB |
| 雄獅 | 1,192 萬 | 921 MB |
| 易遊 | 1,926 萬 | 1.51 GB |
| 山富 | 4,409 萬 | 3.52 GB |
| **可樂錨點比價（全六家）** | | **約 7.5 GB** |

所以：

- **只選需要的欄位。** 絕對不要 `SELECT *`，那會讓成本翻好幾倍。
- **加 `WHERE` 是為了少拿列、不是為了省錢。** 想省錢只能減欄位或減資料表。
- **山富單獨一家就要 3.5 GB。** 使用者只想快速看一眼時，先跑可樂＋雄獅＋東南（約 2.4 GB），需要再補山富。
- 只是要確認「有沒有資料」時，查一張小表就好，不要六家全上。

若 `bigquery_query` 回報「查詢預估掃描 N bytes，超過上限」，那是保護機制正常運作。**不要試圖繞過**，改成減欄位、減資料表，或請使用者縮小範圍。

## 資料品質注意事項

- **同一行程會有多筆**，票價略有差異（不同抓取時間、不同票規）。查價一律 `GROUP BY` 配對鍵後取 `MIN`。
- **可樂有「票型」欄位**，值為 `票面` 或 `淨價`。淨價是不含佣金的成本價，票面是牌價。做成本分析時要分開看，別混在一起平均。
- **可樂另有 `總售價`**（含加價成數），`基礎票價` 是加價前的。跟其他家的 `票面價格` 對等比較要用 `基礎票價 + 稅金`；使用者問可樂實際售價再給 `總售價`。
- 各家含稅總價可能相同但票面／稅金拆分不同，比較時以含稅總價為準。

## 絕對不要做的事

- 不要編造票價、航班編號或日期。查不到就說查不到。
- 不要把沒資料的日期換成鄰近日期後直接回答，要先問過使用者。
- 不要用 `去程降落機場1` 當目的地（見地雷 1）。
- 不要跨艙等比價（見地雷 2）。
- 不要承諾這些價格可以成交——這是爬蟲抓到的**參考報價**，實際票價以各旅行社官網為準，回覆時要帶到這句。
- 不要用 `New_cola_air_tickets_price` 或 `cola_air_tickets_price` 代表可樂。
- 不要嘗試寫入或修改資料（見「唯讀」那節），這個工具只能查詢。
